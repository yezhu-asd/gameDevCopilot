# GameDevCopilot 面试讲解材料

## 3 分钟电梯陈述

> 我做了一个「一句话生成游戏原型」的 AI Agent 系统。用户输入「做一个塔防游戏」，系统自动完成三件事：
> 第一，从游戏设计知识库检索相关设计规范（RAG）；
> 第二，匹配到已验证的塔防骨架模板，让 Agent 在骨架上填充玩法；
> 第三，用 Godot 引擎无头模式自动跑验证，报错就自动修复，最多 3 轮。
> 最终产出的是一个**真正能运行的 Godot 游戏**，不是一份文档或一段代码。整个过程在网页上实时可见。
> 我的动机是：游戏研发 70% 的试错成本在「想到玩法→验证可玩」这个环节，我想用 Agent 把它从几天缩短到几分钟。

## 深入讲解（对应技术栈，逐层展开）

### 一、整体架构

```
一句话需求
   │
   ▼
① 类型检测 core/templates.py ──命中骨架?──→ 注入已验证骨架
   │
   ├─→ ② RAG 检索 knowledge_base/kb.py ──→ 检索设计文档注入上下文
   ▼
③ LangGraph 工作流 core/workflow.py
   generate → normalize → verify ──通过──→ 产出可运行游戏
                              └──失败──→ fix → normalize → verify (≤3轮)
   │
   └── ④ web 层：进度事件回调 → 前端轮询 → 实时展示
```

### 二、为什么选 LangGraph（对应 JD「主流框架搭建 Agent/Workflow」）

**演进思路**：最初是线性 while 循环（`core/pipeline.py`），后来重构成 LangGraph 状态图（`core/workflow.py`）。

**LangGraph 带来的价值**：
1. **有状态**：每个节点是独立函数，state 在节点间显式传递，可观测、可调试。
2. **条件路由**：`_should_fix` 根据验证结果决定去 fix 还是结束，比 while 循环更清晰。
3. **可扩展**：想加「策划评审」节点或「引擎导出」节点，只需 add_node + add_edge，不动其他逻辑。
4. **与 LangChain 生态打通**：后续可以接记忆、工具、Human-in-the-loop。

**面试追问准备**：
- 「为什么不直接写循环？」→ 循环不可观测、难以插入中间步骤；状态图把每个阶段变成显式节点，适合复杂 Agent 编排。
- 「pipeline 和 workflow 为什么并存？」→ 保留线性版做回归对照，CLI 用 `--workflow` 切换；两者结果一致，证明重构无回归。

### 三、验证闭环（对应 JD「有代码能力，能够检验 Agent 结果」）

**核心设计：Agent 生成的游戏必须真的跑起来才算数。**

1. **Godot 无头模式**：`godot --headless --path <项目> --quit-after 5`，毫秒级运行 + 退出返回状态码。这是选 Godot 而非 Unity 的关键原因——项目是纯文本格式、命令行无头成熟、GDScript 对 LLM 生成友好。
2. **错误提取**：解析运行日志，抓 `ERROR:`/`SCRIPT ERROR:` 等模式，去重后作为修复 Agent 的输入。
3. **静态检查层**：额外扫描 Godot 3 遗留 API（`KinematicBody2D`、`StaticBody`、`randi()` 等），在运行前就拦截一批常见错误。
4. **确定性规范化层**：对模型输出做机械修正——Godot3→4 重命名、tscn 资源顺序重排（ext_resource 必须在 sub_resource 前），这些弱模型常犯的确定性错误直接修掉，让修复循环只处理真正的逻辑问题。

**面试追问准备**：
- 「验证能证明设计合理性吗？」→ 不能。验证的是**可运行性**（语法/资源/类型），不是设计优劣。设计质量靠骨架模板约束 + 人工试玩迭代。
- 「为什么加静态检查而不是全交给修复循环？」→ 修复循环成本高（每次 LLM 调用 + 验证），静态检查秒级、零成本，能拦掉 90% 的机械错误。

### 四、RAG 游戏设计知识库（对应 JD「构建知识库与 RAG」）

1. **语料**：74 篇游戏设计文档（概念/参考/领域导航），带 frontmatter 元数据（title/summary/category）。
2. **向量化**：bge-m3 模型，AutoDL GPU 上跑，产出 842 个 1024 维向量。
3. **检索**：FAISS 索引（IndexFlatIP 内积），查询时取 top-3 文档注入 system prompt。
4. **chunk 策略**：按 markdown 二级标题切分，段落聚合，摘要前置——让每个 chunk 自带文档主旨，即使正文长也能命中。

**面试追问准备**：
- 「为什么 embedding 放 AutoDL 跑？」→ GPU 向量化快（CPU 5-10 分钟 vs GPU 1 分钟），且本地有 bge-m3 模型复用。
- 「检索质量怎么验证？」→ 数值平衡查询命中 0.745 相似度；塔防查询命中战术推理等语义相关文档。

### 五、骨架模板（对应 JD「快速构建 Agent 原型」）

**为什么加骨架**：纯靠 LLM 从零生成复杂游戏，结构（节点层级、信号连接、资源引用）容易出错，弱模型尤甚。

**做法**：预置三个**已验证可运行**的最小骨架（platformer/roguelike/tower_defense），命中类型时注入 prompt：
> 「请保持文件结构/节点名/信号/方法签名不变，根据需求填充玩法」

**效果**：塔防生成保留骨架结构，额外填入了波次系统、击杀奖励；一次通过率从多轮下降到 1 轮。

**面试追问准备**：
- 「这不就是模板拼接吗？」→ 骨架是**执行载体**（结构正确性），玩法内容（数值、机制、关卡）仍是 LLM 生成。模板管结构，LLM 管创意。

### 六、前端 Demo（对应 JD「方案设计与落地实施」）

FastAPI + Jinja2 + 原生 JS。核心：`run_pipeline` 增加 `on_progress` 回调 → 事件写入内存 JobStore → 前端轮询 `/api/jobs/{id}` 渲染时间线。

**踩坑实录**（能体现工程能力）：
1. 新版 Starlette `TemplateResponse` 签名变化导致 500。
2. 前端轮询用 DOM 节点数当事件索引，导致 `verifying` 重复渲染——改为事件计数追踪。

## 深挖准备（可能被追问的方向）

### 1. 模型选型
- **glm-4-flash**：免费但 Godot 语法掌握差，一直输出 Godot3 的 `KinematicBody2D`。
- **glm-4.6**：更强但账号额度不足（429）。
- **最终 deepseek-v4-flash**：复杂 Roguelike 1 轮修复通过。
- **启发**：Agent 工程质量高度依赖底层模型能力；对弱模型要用确定性修正层兜底。

### 2. 成本与性能
- 每次生成：1 次 LLM 调用（生成）+ 最多 3 次修复调用 + 多次无头验证。
- 骨架 + RAG 显著降低修复轮次 → 降低 token 成本和延迟。

### 3. 如何扩展（体现架构思维）
- **新玩法类型**：加一个骨架目录 + 关键词 → 自动支持。
- **新知识域**：往 knowledge_base 加文档，重建索引即可。
- **人工审核环节**：LangGraph 加 Human-in-the-loop 节点。
- **多引擎适配**：把验证层抽象成接口，Godot 已实现，可加 Unity 适配器。

### 4. 不足与诚实边界
- 验证的是可运行性，不是好玩性。
- 复杂玩法（多关卡、联网、3D）超出当前能力。
- 知识库规模有限，覆盖常见 2D 玩法。
